# 应用内更新 —— 设计与发布流程

定制版（`com.legado.app.custom`，自建签名）的「检查更新」**不走上游 Release**。
原因：包名与签名都不同，装上游 APK 等于又多装一个官方版，既覆盖不了本应用，数据也不在那边。

---

## 一、数据流

```
App  ──GET──> updates.json（三个镜像依次尝试，任一成功即用）
                ├─ raw.githubusercontent.com/byl669/legado-lyrics-overlay/master/updates.json   ← 最实时
                ├─ cdn.jsdelivr.net/gh/byl669/legado-lyrics-overlay@master/updates.json          ← 国内可达
                └─ fastly.jsdelivr.net/gh/...                                                    ← 兜底
                    ↓
              versionCode > 当前 versionCode ?
                    ├─ 否 → 「已是最新版本」
                    └─ 是 → UpdateDialog（Markdown 更新说明 + 下载）
                              ↓
                        releases/latest/download/Legado-lyrics-overlay-latest.apk
                        （备用：releases/download/<tag>/…  镜像：ghfast.top / gh-proxy.com）
```

**版本比较只用 `versionCode` 整数，不比较版本字符串** —— 避免 `3.26101921` 这类时间戳式命名在不同构建下误判。

## 二、updates.json 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `versionCode` | ✅ | 整数，唯一比较依据 |
| `versionName` | ✅ | 展示用，与 APK 内 versionName 保持一致 |
| `url` | ✅ | APK 直链，固定用 `releases/latest/download/Legado-lyrics-overlay-latest.apk` |
| `backupUrl` | | 指定 tag 的直链，绕过 latest 解析 |
| `mirrorUrl` / `alternateMirrorUrl` | | 国内代理镜像（ghfast.top / gh-proxy.com） |
| `size` | | 字节数，弹窗显示文件大小 |
| `sha256` | | APK 校验值（留档、人工校验用） |
| `notes` | ✅ | Markdown 更新说明，直接渲染到弹窗 |
| `pubDate` | | ISO 8601，带时区，如 `2026-10-19T21:57:00+08:00` |

## 三、发布一个版本（一条命令）

```bash
# 1) 编译（versionCode 递增，versionName 显式给出以免同小时重名）
cd legado
JAVA_HOME=$HOME/.cmfa-toolchain/jdk ./gradlew \
  -g <绝对路径>/.gradle-home \
  -PversionCode=38204 -PversionName=3.26101921-r6 :app:assembleRelease

# 2) 发布（上传 APK + 生成并提交 updates.json + 校验三镜像）
cd ../.publish-staging
tools/publish-release.sh \
  --apk ../dist/Legado-3.26101921-r6-….apk \
  --version-code 38204 \
  --version-name 3.26101921-r6 \
  --tag r6 \
  --notes-file /tmp/r6-notes.md
```

脚本做的事：创建 Release → 上传资产（同名先删，可重复执行）→ 生成 `updates.json` → commit & push → 三个镜像探活。

> Release 资产名固定为 `Legado-lyrics-overlay-latest.apk`（ASCII）。
> 这样 `releases/latest/download/<固定名>` 永远有效，不必每版改清单里的路径。
> GitHub 会把中文文件名清洗成 `.-.`，历史踩过坑，务必用 ASCII。

## 四、代码位置

| 文件 | 职责 |
|---|---|
| `app/src/main/java/io/legado/app/help/update/AppUpdate.kt` | 分流：`appVariant == UNKNOWN`（自建签名）→ `AppUpdateCustom`，否则维持上游 `AppUpdateGitHub` |
| `app/src/main/java/io/legado/app/help/update/AppUpdateCustom.kt` | 多镜像读 `updates.json`、按 versionCode 比较、明确失败信息 |
| `app/src/main/java/io/legado/app/ui/about/UpdateDialog.kt` | 上游原有弹窗，未改动（Markdown 正文 + 下载/忽略） |
| `app/src/main/java/io/legado/app/ui/about/CheckAppUpdate.kt` | 上游原有入口，未改动 |
| `updates.json` | 仓库根目录，唯一数据源 |

自动检查：`MainActivity.upVersion()` 每 24 小时（开关 `autoUpdateVariant`，默认开）自动查一次，
命中后弹同一个 `UpdateDialog`；`LocalConfig.ignoreUpdateVersion` 支持「忽略此版本」。

## 五、失败策略（硬规矩）

- **所有镜像都失败 → 明确报「检查更新失败：<原因>」**，绝不静默提示「已是最新」。
- 清单解析成功但 `versionCode` 不大于当前 → 「已是最新版本」。
- 下载失败由 `Download` 通知栏报错，弹窗里可用「在浏览器中打开」兜底。

## 六、缓存延迟（重要）

`raw.githubusercontent.com` 的响应头是 `cache-control: max-age=300`（Fastly CDN），
且 **query 参数不影响缓存键**（`?t=123` 拿到的仍是旧内容）。实测：

- 推送 `updates.json` 后，raw 最长 **5 分钟** 才返回新内容；
- jsDelivr `@master` 缓存最长 12 小时（因此只作兜底）。

含义：**发布后立刻点「检查更新」可能仍看到「已是最新版本」**，等几分钟即可。
`tools/publish-release.sh` 末尾会打印三个镜像的当前 `versionCode`，若为旧值属正常。

## 七、注意

- **旧版本无法自更新到新版本**：r5 及更早的包更新逻辑还指向上游 Release，
  必须先手动装一次 r6（带本功能），此后应用内更新才闭环。
- 改 `updates.json` 后若要让已装用户立刻看到，可先通知「过几分钟再试」。
- token 只从环境变量或 `~/WorkBuddy/keys/github-pat.txt` 读取，**不写入仓库**。
